> 修复日期：2026-10-04

> 文档整理：2026-10-21

> 严重程度：P1（范围逻辑）、P2（样式）  
> 影响范围：运行总览、设备出力、系统/设备灵活性、能流平衡及构成统计

合并原主目录 BUG-008、BUG-011、BUG-012，以及 BUG-019 中仅诊断的全年滑块性能说明。能流设备表的等宽三列布局移至 BUG-003，避免两处重复维护。

## 1. 问题描述

最初运行总览和设备灵活性缺少滑块。增加后，日期和滑块又绑定同一组值，无法“日期粗选、小时细调”；能流图没有局部窗口，设备出力百分比默认从零起算，非零起点会偏移。设备出力时间段、系统灵活性、能流平衡的灰色滑块与时间点追溯的蓝色圆形样式也不一致。

预期：默认范围以任务实际日期为准，日期框约束滑块边界，滑块驱动最终显示及统计；指定页面使用蓝色控件，其他页面继续灰色。全年拖动性能差异单独分析，不将样式统一表述为性能修复。

## 2. 定位过程与历史验证

静态核对确认：TaskSeriesChart 和 DeviceFlexibilityChart 原来仅使用固定任务起止；公共 DualRangeSlider 已支持分钟范围。后续各页面将日期和滑块同时绑定 rangeStart/rangeEnd，缺少日期父级状态；设备出力用 maximumMinute×percentage，未补 minimumMinute。时间点追溯则是局部原生 range，其他页面使用公共灰色双端组件。

## 3. 根因确认

各图表的时间状态没有形成任务范围 → 日期窗口 → 最终显示时段的层级。样式问题则来自双端公共控件与时间点追溯的独立实现。全年卡顿来自更新时的数据处理与绘图负担，不由滑块颜色决定。

## 4. 修复方案与最终规则

### 4.1 补齐窗口并同步图表

运行总览按时层时间戳推导步长和边界，设备灵活性按 time_step 推导边界。最终时段同时过滤数据并设置 x 轴 min/max；设备峰值随可见数据更新。实时数据边界增长时，仍停留在右端的用户自动跟随；已选历史窗口时保留选择。

### 4.2 两级时间状态

```typescript
const dateRangeStartMinutes = ref(0)
const dateRangeEndMinutes = ref(DAY_MINUTES)
const rangeStartMinutes = ref(0)
const rangeEndMinutes = ref(DAY_MINUTES)
```

日期窗口默认取任务配置范围；修改日期将滑块重置为该窗口全宽。滑块 min/max 为日期窗口，最终 range 控制主图、能流环形图、设备表及其他可见统计。终止日期包含当天，内部按半开区间处理。运行中尚未返回的配置时段可以暂时为空。

### 4.3 非零起点百分比换算

```typescript
const timelineSpanMinutes = computed(() => maximumMinute.value - minimumMinute.value)
const rangeStartMinute = computed(() =>
  minimumMinute.value + timelineSpanMinutes.value * props.zoomStart / 100
)
```

反向换算同样先减 minimumMinute，避免非零任务起点偏移。

### 4.4 两套控件的适用范围

| 页面 | 控件及外观 |
|---|---|
| 运行总览、设备灵活性 | DualRangeSlider，保留灰色 |
| 设备出力时间段、系统灵活性、能流平衡 | PrimaryDualRangeSlider，主色蓝轨道、14px 白底蓝边圆形端点 |
| 设备出力时间点追溯 | 原局部单滑块，作为蓝色视觉基准 |

蓝色边框为 2px #0A4DA2，底轨为 bg-app-border。仅替换指定页面组件，不用全局 CSS 改写全部控件；日期和数据过滤语义保持一致。

## 5. 预期结果与副作用

日期框负责粗选，滑块负责窗口内细调，图表与明细同步。改日期会主动重置小时范围，这是防止旧选择落在新窗口外的预期行为。两套颜色按页面有意保留，后续维护应选择对应组件。

## 6. 全年滑块性能分析（原记录，仅说明，未优化）

灰色与蓝色滑块都在 input 时即时发出视窗更新，颜色本身不是性能差异来源。

- 运行总览 `TaskSeriesChart.vue` 使用 `sliceTimeSeries` 二分定位窗口，绘制前通过 `downsampleTimeSeries` 将大窗折线压到约1200点；`useVisibleChart` 合并同帧更新，屏幕外只标脏，并关闭曲线动画。
- 系统灵活性三个区块共享视窗。一次拖动会更新需求来源、上调与下调图；两个 `FlexibilitySeriesChart` 各重画系统时序和设备贡献图。它们对窗口中的完整结果及 device_results 反复聚合，没有总览同等的抽稀；系统图还构造裕度正负交点、缺额标记，系统图和贡献图均开启220ms更新动画。需求来源图虽已用可见帧调度，其 sourceLines 仍保留完整显示窗点集。
- 能流分析各总线及时层共享视窗，每个 `EnergyFlowChart` 的 watcher 直接调用 renderChart；先扫描各变量全年数组，构造时间集合并排序，再为源/荷重新过滤和建 Map。时间轴抽稀发生在这些扫描之后，并未免去原始数据准备成本；窗口变化也会使依赖该窗口的统计失效。没有总览同等的屏幕外图表跳过机制。

因此差异主要来自拖动时浏览器主线程承担的数据扫描、联动聚合和绘图量。以上为当前代码证据，不是浏览器性能剖析所得的耗时占比；本轮未更改相关调度、动画、抽稀或统计逻辑，也不声称卡顿已修复。
