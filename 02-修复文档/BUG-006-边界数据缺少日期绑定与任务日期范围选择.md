# BUG-006：边界数据缺少日期绑定与任务日期范围选择

> 修复日期：2026-09-29
> 状态：已定位、已修复、待回归验证
> 严重程度：P1 — 多月/全年边界无法按自然日期选择仿真范围
> 影响范围：无日期列 CSV 的边界导入、离线任务创建、边界截取及结果时间展示

> 后续规则变更（2026-10-04）：边界已取消“仅按时长”入口，统一绑定自然日期；缺少日期时默认从 2026-01-01 开始。当前规则及历史数据迁移见 `BUG-007-边界日期与能流展示规则不统一.md`。

---

## 1. 问题描述

**用户操作路径**：

1. 在边界配置页导入一列按固定时间尺度排列、但不含日期列的 CSV 数据
2. CSV 可能是 24 小时典型日，也可能是数月或全年 8760 小时数据
3. 创建仿真任务，希望从全年数据中只选择 7 月 1 日至 9 月 30 日进行仿真
4. 在结果页查看对应自然日期的坐标、提示和时间窗口

**预期行为**：边界导入时可以选择是否绑定日期；日历边界保存真实覆盖范围，任务只能在相关边界的共同覆盖范围内选日期，后端按日期截取数据，结果时间轴显示真实日期。24 小时典型日仍可只按时长使用。创建任务时起止日期分行完整显示，“仿真日期”标签在两项输入之间垂直居中，“边界可选日期范围”和“当前仿真时长”在同一行明确展示。

**实际行为**：边界只保存 `0:00...H:MM` 相对时间，没有自然日期锚点；任务只能填写 `0:00-8760:00` 一类累计小时范围；边界注入只从序列开头取固定长度，无法表达“全年数据中的 7 月至 9 月”；结果滑块也只能显示累计小时。

## 2. 定位过程

### 2.1 初始假设

| 编号 | 假设 | 对应症状 | 初始置信度 |
|---|---|---|---|
| H1 | `BoundaryItem` 和 `boundary_config` 没有日期语义及覆盖日期字段 | 导入后无法知道第一个数据点对应哪一天 | ⭐⭐⭐⭐⭐ |
| H2 | 任务接口和 `tasks.db` 只保存相对时间 | 历史任务无法复现所选自然日期，结果页也无日期映射依据 | ⭐⭐⭐⭐⭐ |
| H3 | 边界 seed 仅按时长截取序列前缀，没有按日期计算偏移量 | 选择 7 月至 9 月时仍会取 1 月开始的数据 | ⭐⭐⭐⭐⭐ |
| H4 | 单纯把任务输入框改成日历即可解决 | 前端看似可选日期，但后端仍可能取错数据 | ⭐⭐ |

### 2.2 日志/调试方案设计

本问题属于数据契约缺失，不需要在运行主循环中增加大量临时日志。定位采用“契约字段检查 + 日期换算脚本 + 语法/构建检查”，避免为确定性结构问题引入长期噪声。

#### 检查点 1：[CONTRACT] — 边界与任务字段

**文件**：`types/boundary.ts`、`types/api.ts`、`backend/services/boundary_service.jl`、`backend/services/task_manager.jl`

**思路**：搜索日期字段及 SQLite 建表语句。如果 H1/H2 成立，原结构中只能看到 `boundaryLength/boundaryStep` 和 `sim_start_time/sim_end_time`，不会出现日期锚点。

**检查命令**：

```powershell
rg -n "boundaryMeta|boundary_config|sim_start_time|sim_end_time|calendar|sim_start_date" types backend
```

#### 检查点 2：[SLICE] — 边界截取偏移

**文件**：`backend/services/boundary_service.jl` — `seed_task_boundary_data`

**思路**：检查截取点的起始下标。如果 H3 成立，旧逻辑会直接执行 `sorted_ts[1:truncate_count]`，而不是根据任务日期与边界起始日期之差计算 offset。

**修复后的关键实现**：

```julia
source_start_minutes = Dates.value(task_start_date - boundary_start_date) * 24 * 60
source_end_minutes = source_start_minutes + calendar_duration_minutes
selected_indices = findall(eachindex(sorted_ts)) do index
    source_minute = time_label_to_minutes(sorted_ts[index])
    source_minute >= source_start_minutes && source_minute < source_end_minutes
end
```

#### 检查点 3：[DATE] — 日期换算边界值

**文件**：`utils/calendarTime.ts`

**思路**：用纯函数验证全年覆盖终止日、跨月包含天数和结果时间标签。该检查不依赖 UI 或数据库，能直接证伪日期换算中的时区偏移和 off-by-one。

**实际执行代码**：

```javascript
import('./utils/calendarTime.ts').then(m => {
  console.log('[DATE] 8760h coverage:', m.deriveCalendarEndDate('2025-01-01', 365))
  console.log('[DATE] Jul-Sep days:', m.inclusiveCalendarDayCount('2025-07-01', '2025-09-30'))
  console.log('[DATE] task label:', m.formatCalendarMinute('2025-07-01', 24 * 60 + 60))
})
```

### 2.3 日志结果

- `tasks` 只保存 `sim_start_time/sim_end_time`。

### 2.4 分析与排除

**H1（边界缺少日期契约）被确认**：前端类型、项目轻量元信息和 boundary SQLite 均无日期锚点，CSV 数据无法绑定到自然日期。

**H2（任务不保存日期）被确认**：任务创建请求、任务表和返回 DTO 都只有相对时间，结果页没有稳定的日期映射来源。

**H3（seed 只截取前缀）被确认**：旧逻辑的起始下标固定为 1，仿真范围即使长度正确，也不能定位到全年数据中的指定月份。

**H4（只改日历输入框即可）被排除**：如果不同时扩展 SQLite、任务快照和 seed 偏移，界面选择的日期不会改变实际输入数据，反而会制造更隐蔽的计算错误。

## 3. 根因确认

根因是系统只建立了“相对时长”模型，没有建立“CSV 序列索引 ↔ 自然日期”的数据契约。`types/boundary.ts:10`、`backend/services/boundary_service.jl:174` 和 `backend/services/task_manager.jl:31` 是本次补齐契约的直接位置。

与此同时，旧 seed 逻辑仅按仿真时长从序列开头截取。修复后的 `backend/services/boundary_service.jl:636` 根据任务起始日期与边界起始日期之差计算分钟偏移，并在截取后把时间戳重新标记为任务局部 `0:00...`，因此不改变既有求解模型的时间语义。

---

## 4. 修复方案

### 4.1 边界导入增加显式时间语义

```typescript
export type BoundaryTimeMode = 'duration_only' | 'calendar'

export interface BoundaryMetadata {
  boundaryLength: string
  boundaryStep: string
  dayCount: number
  pointCount: number
  timeMode: BoundaryTimeMode
  calendarStartDate?: string
  calendarEndDate?: string
}
```

- “仅按时长”适用于 24 小时典型日或不关心日期的数据；
- “绑定日期”要求选择起始日，CSV 第一个数据点对应起始日 `00:00`；
- 终止日由截断后的数据点数和时间尺度自动计算，不允许手填不一致范围；
- 日期为空时统一显示“年/月/日”，不依赖浏览器本地化生成的 `yyyy/mm/日` 提示；实际值仍使用 `YYYY-MM-DD`；
- `boundary_config` 通过向前迁移增加 `time_mode/calendar_start_date/calendar_end_date`，旧记录默认 `duration_only`。

### 4.2 任务创建按相关边界决定控件

- 当前画布相关边界全部为日历模式时，显示起止日期控件；
- 可选范围取所有相关边界覆盖区间的交集；
- 全部为仅按时长时，保留原 `H:MM-H:MM` 输入；
- 两种模式混用或日历范围无交集时，前后端均拒绝创建，避免静默错位。

日历任务仍发送 `simStartTime="0:00"`，`simEndTime=包含天数×24:00`，并额外发送 `simStartDate/simEndDate`。

### 4.3 后端按日期截取并保持求解器兼容

```text
边界 CSV 数据点
  → boundary_config 绑定覆盖日期
  → 创建任务选择共同覆盖范围内日期
  → seed 计算源序列 offset 并精确截取
  → 截取结果重标为任务局部 0:00...duration
  → 现有模型和时层滚动逻辑保持不变
```

seed 只处理当前画布引用的 `boundaryIds`；没有显式 ID 的旧项目回退到 `relatedComponents` 匹配，避免项目中无关边界参与日期校验。

### 4.4 结果时间展示

- 任务表保存日期范围，任务信息栏显示自然日期；
- 运行总览、能流、设备出力和灵活性图表将任务局部分钟映射为 `M月D日 HH:mm`；
- 设备出力和灵活性时间窗口保留双端滑块，并在日历任务中增加起止日期输入；
- 旧任务或仅按时长任务仍显示原 H:MM，不需要数据迁移。

## 5. 预期结果与副作用

| 指标 | 修复前 | 预期修复后 |
|---|---|---|
| 8760h 数据日期覆盖 | 无法表达 | 起始日 + 365 天自动得到终止日 |
| 7 月 1 日至 9 月 30 日仿真 | 只能手算累计小时，且实际取序列前缀 | 自动换算为 92 天，按 7 月 1 日偏移截取 |
| 24h 典型日 | 被迫理解为某个自然日 | 可继续选择“仅按时长” |
| 多边界日期一致性 | 无校验 | 只能在共同覆盖交集内选择 |
| 结果时间标签 | 累计 H:MM | 日历任务显示真实日期，旧任务保持 H:MM |
| 历史数据兼容 | 不适用 | 旧 boundary/task 日期字段为空，按原逻辑运行 |

**副作用与风险**：

- 旧边界默认视为 `duration_only`；要使用日历任务，必须重新进入边界配置，选择起始日并重新提交。
- 当前按完整自然日绑定和选择，暂不支持“7 月 1 日 06:00 至 7 月 3 日 18:00”这类非整日起止范围。
- 日历范围依赖项目元信息与 boundary SQLite 一致；提交接口会同时写入两处，后端 seed 以 SQLite 为最终校验依据。
- 完整 Nitro 打包在本机受限环境中被 `readlink EPERM` 阻断，仍需在正常开发终端执行一次完整构建和 UI 回归。
