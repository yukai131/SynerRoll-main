# BUG-010：容量规划终止按钮无法中断当前求解，场景进度与总时限失效

> 修复日期：2026-10-19
> 状态：已修复，回归结果见第 5 节
> 严重程度：P1
> 影响范围：容量规划进行中的场景求解、排队任务取消、外层总时限；不改变普通仿真的默认求解策略。

## 1. 问题描述

用户操作路径：创建容量规划 → 首个候选完成 → 下一候选某个典型场景长时间求解 → 点击“终止容量规划”。预期释放本次规划计算资源并进入取消状态，实际页面一直显示优化中、评价次数不变，后台仍计算。

## 2. 定位过程

初始假设：①按钮未发请求；②后端只在候选边界消费取消信号；③页面计数不更新被误认为停止；④最长时间未限制内部求解。

通过前端 `cancelPlanning`、BFF cancel、Julia manager、runner 与 simulation evaluator 逐层核对：按钮确实调用取消接口；manager 仅向 Channel 写入 `:cancel`；runner 仅在下一次 fitness 入口检查。实际 `solve_model` 同步调用 `JuMP.optimize!`，其间不检查信号。因而确认②、④；③同时存在，进度只在完整候选结束时增加。

实际任务 `cp-67b25da9-4e3c-4c81-8edd-760ced080646` 的只读检查摘录：

```text
status: optimizing
updated_at: 2026-10-19T15:43:45.759
completedEvaluations: 1
failedEvaluations: 0
第一个候选 duration_ms: 20758
第二个候选 scenario-1 数据库最后写入：2026-10-19T07:45:27.663Z
第二个候选 scenario-2 已创建，尚未完成
```

进度未更新不能证明后台停止；文件证据表明第二个候选已经进入计算。没有向用户数据插入调试记录。

## 3. 根因确认

取消操作的检查点在候选之间，而阻塞位置在候选内部的原生求解器调用。Julia 线程中的协作信号无法可靠中断该调用。外层 BlackBoxOptim 的 MaxTime 同样要等 fitness 返回后才有机会响应；页面没有场景粒度进度，因此表现为既无法取消，也看不到当前计算阶段。

## 4. 修复方案

修改前的数据流：HTTP 进程 → Julia 线程 → 多场景同步求解；取消仅向 Channel 写信号。

修改后：HTTP 进程监督独立的容量规划工作进程。取消只终止本次规划的子进程，等待进程退出、原生求解器和文件句柄释放后，再写入 cancelled；排队且尚未启动的任务直接取消。不会通过结束共享后端来中断规划。

- 新增 `backend/capacity_worker.jl`。复用后端模块加载，跳过监听端口、普通任务启动恢复和服务预热。
- manager 用进程句柄监督、取消、检测异常退出并实施总时限。容量规划工作进程串行启动，保留原来一次运行一个规划的资源约束。
- 总时限从子进程启动计时（含模块加载和首次编译，不含排队时间）；到期终止未完成的求解。若已有完整、落库的可行候选，则返回其中最佳方案并附时限说明；否则明确失败。用户主动取消始终为 cancelled，不包装成 completed。
- 每个典型场景默认最多 60 秒，且不超过所配总时限。只在容量规划中允许使用 TIME_LIMIT 状态下已有的可行解，并记录“尚未证明场景最优”说明。普通仿真仍要求 OPTIMAL。
- 更新候选序号、场景序号与构建/求解/完成阶段；父进程按秒更新耗时，字段更新采用 SQLite 原子 JSON 修改，避免覆盖工作进程进度。
- 前端按钮显示“正在终止…”，保持禁用直到终态；增加场景进度和日志；丢弃切换任务后返回的旧轮询响应。
- 启动恢复将上次后端遗留的非终态任务标为失败，避免永久显示优化中。

取消接口设置原子请求标记，监督循环针对已登记句柄执行 `kill(process)`，并在 `wait(process)` 完成后发布终态。监督循环是终止和等待操作的唯一执行方，避免重复终止及进程退出竞争。没有使用全局 Julia 进程名杀进程。

## 5. 预期结果与副作用

| 场景 | 修复前 | 修复后 |
|---|---|---|
| 场景原生调用阻塞时取消 | 等当前候选返回 | 结束该规划子进程并释放其资源 |
| 候选内计算多个场景 | 只显示完整评价次数 | 显示当前场景、阶段和持续更新的耗时 |
| 300 秒总时限 | 可被内部求解无限超出 | 父进程监督到期停止计算 |
| 其他普通仿真或外部进程 | 不应受影响 | 不对其发送终止信号 |

回归以独立临时数据库执行，覆盖真实工作进程启动与 HiGHS 求解、原生 Sleep 阻塞中取消、排队取消、重复取消、无候选总超时、已有候选总超时和主动取消、独立进程保留、进度心跳及原有经济和 API 用例。最终测试数量和输出见 `docs/容量规划融合记录-2026-10-19.md` 的追加记录。

副作用：每次规划有独立 Julia 启动和首次编译开销，启动时间计入总时限；过短预算可能在产生首个候选前用尽。场景限时取得的可行解会标明未证明最优。此改动需要重启 Julia 后端后生效，已有旧版进程中的任务无法通过新代码热替换控制。

## 6. 调试日志处理建议

保留每个规划任务 `logs/worker.log`，用于诊断子进程启动、求解器加载和异常退出。保留场景阶段和求解终止状态；不增加逐时刻数据库日志。
