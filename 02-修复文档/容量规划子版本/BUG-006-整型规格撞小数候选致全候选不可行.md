# BUG-006：容量规划全候选不可行（整型规格撞小数候选致建模崩溃）

> 修复日期：2026-09-28
> 状态：已修复（待回归验证）
> 严重程度：P0（阻塞核心流程，容量规划任务 100% 失败）
> 影响范围：所有包含可调容量设备（风机/光伏/储能等）的容量规划任务；凡组件库中字段被推断为 Int64、且优化器产出小数值的候选，均在建模阶段崩溃，最终导致 `NO_FEASIBLE_CANDIDATE`

---

## 1. 问题描述

**用户操作路径**：
1. 画布放置风机（容量 44875 kW）等设备，发起容量规划任务
2. 后端优化器（BlackBoxOptim 差分进化）开始迭代求解
3. 任务详情页最终显示失败：所有候选方案均不可行（`NO_FEASIBLE_CANDIDATE`）

**预期行为**：优化器正常迭代，产出若干可行候选方案及经济性对比。
**实际行为**：每个候选、每个场景评价都抛 `InexactError: Int64(...)`，全部候选不可行，任务失败。

后端日志（摘录，来自用户开发机实际输出）：

```
┌ Warning: 容量规划场景评价失败
│   scenario_id = "scenario-1"
│   exception =
│    InexactError: Int64(35437.5)
│    Stacktrace:
│      [1] Int64 @ .\float.jl:923 [inlined]
│      [2] convert(::Type{Int64}, x::Float64) @ Base .\number.jl:7
│      [3] validate_and_fill_field! @ backend/core/validation.jl:31
│      [5] validate_component_config! @ backend/core/validation.jl:159

│     [13] build_model_tracked @ backend/services/model_service.jl:577

```

错误值随候选变化：35437.5 / 64437.5 / 30437.5 / 27437.5 / 48437.5 / 32437.5。

## 2. 定位过程

### 2.1 初始假设

| 编号 | 假设 | 对应症状 | 初始置信度 |
|---|---|---|---|
| H1 | 优化器本身不收敛/约束配置错误，导致无解 | 全部候选不可行 | ⭐⭐ |
| H2 | 组件校验把优化器给出的小数容量 convert 成 Int64 崩溃（错误发生在建模型阶段，求解从未开始） | 每个候选都炸、错误值 ≡ 437.5 (mod 1000) | ⭐⭐⭐⭐⭐ |
| H3 | 崩溃字段来自 parse_service 组装 component.json 时额外造出的整型字段 | 同 H2 | ⭐⭐⭐ |

### 2.2 日志方案设计

未插入新日志。直接利用 Julia 异常自带的完整堆栈（含类型签名与行号）进行静态定位，关键帧：

- `[3] validate_and_fill_field! @ validation.jl:31` —— `convert(spec.field_type, field_value)`，目标类型 **Int64**；
- `[8] WindTurbine(comp_dict)` —— 崩溃发生在风机组件实例化的参数校验阶段，而非求解阶段；
- 堆栈中无求解器（COPT/JuMP）帧，确认"求解从未开始"。

### 2.3 日志结果

见 §1 摘录。关键数据点：

- 错误值全部满足 `值 = 22437.5 + n × 1000`；
- 22437.5 = 画布风机容量 44875 × 0.5（C-401 变量识别的默认下界系数 `defaultLowerFactor`，见 `backend/services/capacity_planning/variable_detector.jl:70`）；
- 量化吸附锚在下界上（`optimization_runner.jl:38`：`number = lower + round((number - lower) / step) * step`），所以所有候选容量永远带 `.5` 小数。

### 2.4 分析与排除

**H1（求解不收敛）被排除**：堆栈显示异常发生在 `build_model_tracked` 建模型阶段，任何求解器都还没启动；且错误是类型转换异常，与约束、收敛性无关。

**H3（parse_service 造字段）被排除**：通读 `backend/services/parse_service.jl:227-258`，`paras` 仅透传前端 `commonTechParams`，`costs` 显式 `Float64(v)` 转换，不造任何新字段；`component.json` 内容即画布节点参数的忠实投影。

**H2 确认**：`convert(::Type{Int64}, x::Float64)` 说明运行时风机 `paras` 规格表中 capacity 字段的 `field_type` 是 **Int64**。但按工作区 `config/component-library.json` 复算 `backend/core/schema.jl:50 infer_julia_type`：WT 全部 26 个字段均为 Float64/Bool/String——**静态分析与运行时行为矛盾**。

解开矛盾的检查：
1. 全库扫描"整数 defaultValue + 非浮点 step"字段 → 命中 `GRID.capacity`（`defaultValue: 1000000`、`step: 10000`、`min: 0`，全为 JSON 整数写法），该字段在**本工作区副本**即被推断为 Int64；
2. 由此确认推断逻辑存在真实漏洞：只要 JSON 用整数写法，带 step 的可调浮点字段就会被判成 Int64；
3. 用户开发机上的组件库副本与本次工作区副本不一致（浮点/整数写法混用、副本间存在同步差），风机 capacity 在其运行环境中被推断为 Int64；
4. "以前没问题"的解释：C-401 之前 capacity 不是决策变量，画布值为手填整数（44875），`convert(Int64, 44875)` 不炸；C-401 之后优化器产出带 `.5` 的连续量化值，首次撞上 Int64 规格。

---

## 3. 根因确认

`infer_julia_type`（`backend/core/schema.jl:71-77`）对"整数 defaultValue"的字段用 **`step` 的 JSON 数值写法**判断是否浮点：只有 `step isa AbstractFloat` 才返回 Float64。组件库 JSON 数值写法不统一（同一文件内 WT.capacity 写 `300000.0/1000.0`、GRID.capacity 写 `1000000/10000`），导致一批语义上可调的浮点字段（带 step）被推断为 Int64。容量规划（C-401）把 capacity 变为优化变量后，量化候选锚在下界 `current×0.5` 上必然带小数（如 35437.5），建模校验 `convert(Int64, 35437.5)` 抛 `InexactError`，异常冒泡至场景评价，该候选记为不可行；所有候选同因全灭 → `NO_FEASIBLE_CANDIDATE`。

---

## 4. 修复方案

两处修改，均在 `backend/core`：

**修改 1（治本）——`schema.jl` `infer_julia_type`**：整数 defaultValue 的字段，**只要有 step**（无论整数还是浮点写法）即按 Float64 处理；仅无 step 的整数字段保留 Int64 语义。

```julia
# 修改前：
    elseif dv isa Integer && !(dv isa Bool)
        # JSON3 会把 3.0 解析为 Int64(3)，用 step 的类型判断是否为浮点数
        step = get(field_data, "step", nothing)
        if step isa AbstractFloat
            return Float64
        end
        return Int64

# 修改后：
    elseif dv isa Integer && !(dv isa Bool)
        # JSON 数值写法不统一（300000 与 300000.0 并存），只要字段带 step 就是可调浮点量，
        # 一律按 Float64 处理，与 step 自身的数值写法无关；只有无 step 的整数字段才保留 Int64 语义
        step = get(field_data, "step", nothing)
        if step isa Real
            return Float64
        end
        return Int64
```

**修改 2（保险）——`validation.jl` `validate_and_fill_field!`**：宽容转换加保护壳 `_convert_field_value`，整型规格遇到非整数值时取整并 `@warn`（带字段路径、原值、目标类型），不再让整个规划任务在建模阶段崩溃，且今后同类报错可直接看到字段名。

```julia
# 修改前（validation.jl:31）：
            data_dict[field_name] = convert(spec.field_type, field_value)

# 修改后：
            data_dict[field_name] = _convert_field_value(field_path, field_value, spec)

# 新增函数：
function _convert_field_value(field_path::String, field_value::Real, spec::FieldSpec)
    try
        return convert(spec.field_type, field_value)
    catch err
        err isa InexactError || rethrow()
        rounded = round(spec.field_type, field_value)
        @warn "field value rounded to fit integer spec" field_path field_value spec.field_type rounded
        return rounded
    end
end
```

## 5. 预期结果与副作用

| 指标 | 修复前 | 预期修复后 |
|---|---|---|
| 含风机容量变量的规划任务 | 100% 失败（NO_FEASIBLE_CANDIDATE） | 正常产出候选方案 |
| GRID.capacity 等整数写字段 | Int64 规格（小数即崩） | Float64 规格 |
| 全库 Int64 规格字段数 | ≥1（GRID.capacity） | 0 |

**副作用**：
- 修复后全库已无 Int64 规格字段（已全量扫描确认），Int64 推断分支成为事实上的死代码，行为变化为零；
- 修改 2 的 `@warn` 在触发时会按候选×场景频次输出警告，正常路径不可达，仅为安全网；
- 候选容量取整仅发生在"规格确为整型却收到小数"的异常路径，不改变正常候选值分布（量化语义保持 C-401 原样）；
- 后续可跟进：统一组件库 JSON 数值写法（整数 token 一律改浮点），从数据源头消除歧义。
