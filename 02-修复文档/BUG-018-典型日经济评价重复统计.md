# BUG-018：容量规划经济评价将日层重复窗口计入典型日费用

> 修复日期：2026-10-19
> 状态：已修复，隔离回归通过
> 严重程度：P1
> 影响范围：容量规划后验运行成本、生命周期年度收入/成本/电量及派生经济指标。

## 1. 问题描述

用户启动容量规划后，首个候选运行成本异常巨大。核对模型目标与后验成本，发现后验成本约为模型目标的两倍。预期一个典型日仅计入该日 24 小时的数据。

## 2. 定位过程

初始假设：①确有大量供需松弛惩罚；②典型场景权重错误；③日层滚动结果被重复累计。只读检查任务 `cp-67b25da9-4e3c-4c81-8edd-760ced080646` 的首个候选：

```text
weightedOperatingObjective = 289252450327860.25
weightedOperatingCost      = 578504699454071.8
weightedSlackCost          = 578498707803610
各场景松弛序列行数         = 48
最小 ts_min                = 0
最大 ts_min                = 2820
```

①和③同时被确认。权重合计为 365 天，没有发现该例的代表天数重复。约 99.999% 的后验成本来自热能和氢能过剩惩罚；但 48 点序列代表两个重复日，经济评价又将这两个日的数据全部累计。

## 3. 根因确认

主版本 `model_utils.jl:generate_result_ts` 对日层使用 `duplicate_values` 保存两天数据，以支持滚动读取。容量规划 `evaluate_scenario_operating_cost` 读取组件出力、价格及松弛时传入 `sim_end=nothing`，因此连同第二天的重复窗口一起统计。

## 4. 修复方案

仅修改容量规划后验经济评价，将上述所有读取统一限制为半开区间 `[0:00, 24:00)`。日层运行结果的复制机制、普通仿真的读取和存储格式保持不变。

```julia
# 修改前
load_component_data(db_path, code, comp_type, layer_id, "0:00", nothing)
# 修改后
load_component_data(db_path, code, comp_type, layer_id, "0:00", "24:00")
```

价格边界、松弛惩罚和 LCOE 电量读取采用相同终点。经济评价中的 SQLite 句柄通过 finally 关闭，包括异常路径。

## 5. 预期结果与副作用

测试将每个场景的第二天出力、售电及松弛设置为极大值，验证它们不影响第一天成本、年度折算、NPV 和 LCOE；相关断言已通过。其余真实 HiGHS 求解和方案比较回归同时保留。

修复后新任务的后验数值会变化。旧任务已保存的结果没有自动重算，需要重新规划；实际热、氢过剩及其惩罚仍存在，截取正确时间范围不会消除物理供需问题。

## 6. 调试日志处理建议

本次未增加生产插桩。保留已有模型目标、后验成本和场景权重，方便对照；回归中保留带第二天极大值的数据库算例。
